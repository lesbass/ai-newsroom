## Findings fixed in this heartbeat

Commits `3fa4276` and `c8efb8e`, pushed to `main`.

### F1 — Mobile article-card tick collided with the headline text

`@media (max-width: 600px)` overrode `.article-card` padding to `1rem 0.5rem`, dropping the left
gutter from `1.15rem` (the base value) to `0.5rem`. The `::before` tick is `left: 0; width: 0.48rem`,
so it ended up *inside* the text's leading edge.

`src/layouts/BaseLayout.astro:692` → `.article-card { padding: 1rem 0.5rem 1rem 1.15rem; }`
(restores the base gutter; right/top/bottom unchanged).

**Measured**, first `.article-card` on `/articles/`, 390×844, `deviceScaleFactor: 4`. "Geometric" is
`title.left − (card.left + tick.left + tick.width)`. "Ink" is a pixel scan of the tick's own
horizontal band in the card screenshot (background sampled inside the band, |ΔRGB| > 40, device px
÷ 4).

| Metric | Before (`51bcced`) | After (`c8efb8e`, live) |
|--------|--------------------|--------------------------|
| `.article-card` `padding-left` | **8px** | **18.4px** |
| Geometric tick → title gap | **0.33 px** | **10.72 px** |
| Pixel ink gap (tick end → first glyph) | **0.75 px** | **11.00 px** |
| Tick ink width | 8 px | 8 px (unchanged) |

Desktop (1366×768) control, same probe: **10.72 px geometric / 14.25 px ink before and after** —
unchanged, confirming the change is scoped to the ≤600px override only. Mobile now matches the
desktop gutter exactly.

Before/after were measured with the same script against (a) a detached `git worktree` build of
`51bcced` served locally and (b) production after deploy.

`.card-featured { padding: 1rem }` in the same media query leaves an 8.3px tick clearance — within
budget, deliberately left alone.

### F2 — `--color-faint` failed WCAG AA in light mode

`--color-faint: #7a8798` on `--color-bg: #f3f6fb` is **3.37:1** (3.52:1 on `--color-surface`) — below
the 4.5:1 floor for normal text. It is used by exactly two rules, both at 12px:

- `.tag-index-count` — the topic counts on `/tags/`
- `.source-type` — the `[secondary]` label on article source lists

`src/layouts/BaseLayout.astro:196` → `--color-faint: #616d7e`.

| Pair | Before | After |
|------|--------|-------|
| `--color-faint` on `--color-bg` | **3.37:1** ❌ | **4.85:1** ✅ |
| `--color-faint` on `--color-surface` | **3.52:1** ❌ | **5.02:1** ✅ |

Same hue, darkened. Dark mode's `#7f91ad` was already 5.91:1 and was **not** changed — a token that
passes in one scheme and fails in the other is still a failure, so the new check asserts both.

### F3 — The "high-risk claims" badge failed WCAG AA

`.tag-highlight` sets `color: var(--color-highlight)` on `background: var(--color-highlight-subtle)`.
Light-mode `#c2563f` over `rgba(194, 86, 63, 0.11)` composited on `--color-bg` is **3.59:1** for
11.5px text — and `#c2563f` was also only 4.13:1 as `.nav-links a:hover` / `.site-logo:hover` text.

This badge is the site's editorial trust signal for flagged claims; it is the last thing that should
be hard to read.

`src/layouts/BaseLayout.astro:201-202` → `--color-highlight: #a64835` and
`--color-highlight-subtle: rgba(166, 72, 53, 0.11)` (kept on the same base colour so the token pair
stays consistent).

| Pair | Before | After |
|------|--------|-------|
| `--color-highlight` on `--color-highlight-subtle` | **3.59:1** ❌ | **4.63:1** ✅ |
| `--color-highlight` on `--color-bg` (nav/logo hover) | **4.13:1** ❌ | **5.39:1** ✅ |

Dark mode's `#f08a72` was already 6.43:1 / 7.74:1 — unchanged.

`--color-brass` (`#8b6f2f`, 4.39:1) is declared but **referenced by no rule** in `src/`, so it is
not a defect. The `a { text-decoration-color: rgba(200, 79, 56, 0.48) }` underline was left as-is:
the link is identifiable by underline presence (shape), which is the accessible pattern, and
retinting it would restyle every link on the site.

## Control-plane limitation

Every attempted issue **comment** and **status write** from this run failed:

```
POST /api/issues/{id}/comments  -> 403
PATCH /api/issues/{id}          -> 403
{"code":"cross_issue_influence_run_context_required"}
```

even with `X-Paperclip-Run-Id: 6d0fb85b-494a-44da-991c-456cf3aca3a1`.

Cause: `readRunSourceIssueId(run.contextSnapshot)` is `null` for this `heartbeat_timer` run (no
`issueId` in the snapshot), so `crossIssueInfluenceRunContextError()` fires. The guard is enforced in
`server/src/routes/issues.ts` whenever the body carries `updateFields` or `commentBody`.

Two consecutive identical failures were observed, so the retry budget is spent and no further write
attempts were made this heartbeat. Issue **creation** and **deletion** are not behind that guard and
worked normally:

- deleted the stray probe issue created while testing the write path (title `probe`);
- created AIN-867, AIN-868, AIN-869 above.

**Fallback used:** this document under `docs/audit-reports/` is the durable record of the run, per
`AGENTS.md` ("Operational notes, audits, and issue dispositions live under `docs/`"). A board member
or a task-bound run should copy the relevant parts onto whatever issue this heartbeat was meant to
update, and should decide whether timer heartbeats should carry a run-context issue id.
