laid out at `max-content` width. The Sources citation table measured **1557 px wide inside
the 335 px phone column**, and the 4-column prose tables (e.g. the Anthropic cyber-program
tiers) clipped mid-cell, leaving URLs unreadable without horizontal panning.

**Fix — `1e47a1c` "stop article tables clipping into horizontal scroll":**

- Tables are `width: 100%` with `overflow-wrap: break-word`; prose wraps instead of
  stretching the table.
- Sources tables get a generated `<colgroup>` with a bounded URL column, so long URLs wrap
  while the publisher labels keep their width.
- At `≤640 px` every article table renders as stacked, header-labelled cards; the `#`
  ordinal column is hidden. Desktop keeps a normal table, with the scroll wrapper retained
  only as a fallback for genuinely wide tables.

  and the wrapper's accessible name is `Table`.

## 07:15 UTC — reproducible build-image install failure found; Node/npm pinned

**New lead.** Cloudflare's 2026-10-14 changelog raised the Workers Builds default Node.js from
24.18.0 to 24.21.0 (and other tooling). The last green deploy (`b47cf8d`) ran on 2026-10-13,
the day before that change; every build after it has failed. To separate a build-image
regression from an account/integration fault, I replicated the documented Workers Builds
toolchain locally.

**Reproduced failure.** The Workers Builds build image documents npm 10.9.2
(<https://developers.cloudflare.com/workers/ci-cd/builds/build-image/>). A clean
`npm ci` from the current tree under Node 24.21.0 + npm 10.9.2 exits 1 with `ERESOLVE`:

> Conflicting peer dependency: @astrojs/markdown-remark@7.2.0
> peerOptional @astrojs/markdown-remark@"7.2.0" from astro@7.0.2

The same failure reproduces on the last-good tree `b47cf8d`, so it is latent, not introduced
by the recent audit commits. npm 11 tolerates the unmatched *optional* peer; npm 10 does not.
`@astrojs/markdown-remark@7.3.1` is intentional (the `unified()` markdown config), and Astro
`>=7.2.10` accepts `^7.3.0`, but the lockfile still pins Astro 7.0.2.

**Fix applied.**

- `.npmrc`: `legacy-peer-deps=true` so `npm ci` uses the already-resolved lockfile on both
  npm 10 and npm 11. Verified: `npx npm@10.9.2 ci` exits 0, then `npm run build` produces
  593 pages and the full gate is green (check, lint, links, mobile, SEO, sitemap-lastmod,
  images, dates, contrast, targets, glyphs).
- `.nvmrc`: `24.18.0`, the last-known-good Workers Builds runtime, so a future image default
  cannot silently change the build runtime again.
- README deployment table updated with both pins and the reason.

**Still unverified.** This removes a reproducible install failure in the documented build

This run followed up the AIN-1001 open note ("recheck cold-cache latency next cycle")

| Check | Result |

### What looked wrong

Ten sequential `GET /` requests over HTTP/1.1 produced two 25 s timeouts with no response
and `cf-cache-status: HIT` responses with TTFB between **0.12 s and 20.2 s**. A Playwright
navigation to the newest article also hit a 45 s `networkidle` timeout on first load. On a
static edge-cached site that spread is not normal, so it was worth pinning down.

### What it is

The variance tracks the Cloudflare colo in `cf-ray`, not the request path:

| Target | Colo | TTFB samples |
|---|---|---|
| `news.lesbass.com/` | MUC | 0.14, 0.14, 0.14, 0.17 s |
| `news.lesbass.com/` | ZRH | 0.85, 1.76, 2.52, 2.90 s |
| `lesbass.com/` | MUC | 0.18 s |
| `lesbass.com/` | ZRH | 0.77, 0.78, 0.83 s |
| `paperclip.lesbass.com/` | ZRH | 0.87, 0.89, 0.92, 2.56 s |
| `cloudflare.com/` | MXP | 0.06–0.09 s |
| `astro.build/` | MXP | 0.08–0.11 s |
| `github.com/`, `example.com` | n/a | 0.09–0.31 s |

`lesbass.com` and its subdomains resolve to **188.114.96.0/24**; the comparison hosts above
use Cloudflare's 104.16/104.18 ranges and land in MXP at ~70–100 ms. Every `lesbass.com`
property — including the Paperclip app, which is a different codebase — inherits the same
ZRH slowness, and the same-zone nameservers are ordinary Cloudflare (`maria`/`ram`). So the
spread is a property of this runner's network path to that anycast block, not of the news
Worker, the asset binding, or the cache.

No code, cache, `run_worker_first`, or DNS change was made. Re-checking from an independent
vantage (e.g. WebPageTest or a second region) is the right next step before treating this
as user-facing; the ZRH/MUC split means any single-vantage measurement here will be noisy.
