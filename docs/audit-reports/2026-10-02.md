## Changes Shipped This Heartbeat

`scripts/check-seo.mjs` gains a **base-URL guard**.

The SiteEngineer guardrail existed only as prose — nothing failed when a base URL was wrong.
`check-seo` now asserts that every absolute URL a crawler reads for our own pages resolves to
`https://news.lesbass.com`:

- per-page `rel=canonical`, `og:url`, `twitter:url`
- every `<loc>` in `sitemap.xml`
- every `<link>` / `<guid>` / `<atom:link href>` in `rss.xml`
- the `Sitemap:` line in `robots.txt`

It reads the built artefacts when `dist/` exists and falls back to a `CHECK_URL` fetch otherwise, so
the same audit that would ship a bad base URL fails on it. A wrong origin is an **error**, not a
warning (it is a deployment defect), and the bulk lists are aggregated so one bad build prints three
summary lines instead of a thousand.

Proof the guard is live, not decorative — run against a copy with the constant rewritten to
`https://wrong-host.example.com`:


### Visual judgment

**Homepage — desktop.** The masthead, the oversized Fraunces "AI Newsroom" lockup with its dashed
signal marks, and the single featured card read as a deliberate editorial front page rather than a
template. The card sits on a centred ~720 px column while the masthead spans the full grid — the
intentional "signal desk" rhythm. Nothing overlaps, nothing is clipped.

**Homepage — mobile.** Header stacks the logo above a wrapping nav; the accent underline marks the
current section correctly. The featured card is the weak spot: 8 tag pills occupy **4 rows
(~220 px)** between the meta line and the dek, pushing the summary down and making the preview read
as a tag cloud. Tracked as **F2**.

**Article — desktop.** AIN-839's headline step-down works: the three-line `h1` ends at y≈284 of
900, so breadcrumb + headline + meta + tags + the top of the hero screenshot all sit above the fold.
The hero caption carries its source URL, capture date, capture tool and licence note — exactly the
screenshot evidence the editorial policy requires. The tag row (6 pills + `+2` + `high-risk claims`)
is one line and reads as metadata, not clutter.

**Article — mobile.** First screen is breadcrumb (2 lines) + `h1` (4 lines) + meta (2 lines) +
tags (3 rows); the hero begins at y≈1140, i.e. below the 844 px fold. Headline-first, artwork-second
is a reasonable news hierarchy, so this is not filed as a defect — but the three tag rows add
~140 px of preamble that buys little on a 390 px screen. Same root cause as F2.

**Listing `/articles/` — desktop and mobile.** Headline → meta → tags → dek with dividers; no card
feels cramped. Deks are truncated to ~213 chars by `truncateCardDesc()`, so previews stay two to
five lines and never become walls of text. About 1.5 cards fit above the mobile fold — dense enough
to scan without feeling like an infinite feed.

**Tag page `/tags/security/` — desktop and mobile.** "4 articles", an `← All topics` back link and
the same card pattern; renders correctly at both widths. The back-link arrow is the subject of F3.

## Findings

### F1 — plain `http://` serves 200 instead of 301 (new → [AIN-846](/AIN/issues/AIN-846))

`http://news.lesbass.com/` and `http://news.lesbass.com/robots.txt` both answer `HTTP/1.1 200 OK`
with real content and no `location:` header. HSTS (`max-age=31536000; includeSubDomains; preload`)
is only sent on the HTTPS response, so it does nothing for a first-time HTTP navigation. Indexing
impact is mitigated — canonicals, `og:url`, sitemap and RSS all point at HTTPS and the new guard now
enforces that — but the site should not answer plaintext at all. The fix is a Cloudflare zone
setting; it needs the access tracked in [AIN-845](/AIN/issues/AIN-845).

### F2 — tag pills turn mobile card previews into a wall (new → [AIN-847](/AIN/issues/AIN-847))

`src/components/ArticleCard.astro` renders `tags.slice(0, featured ? 8 : 5)` as individual pills
between the meta line and the dek. On the homepage featured card at 390×844 that is 4 rows / ~220 px.
[AIN-847](/AIN/issues/AIN-847) carries the measurement, a presentation-only fix (keep the links in
the DOM, hide the overflow below 640 px, show `+N`), and acceptance criteria that require build plus
checks passing **and** desktop + mobile screenshots before it closes.

### F3 — `←` renders as tofu in the audit browser (observation, no issue)

Every tag page renders its back link as a `.notdef` box followed by "All topics"
([crop](2026-10-02/crop-alltopics-desktop.png)). The root cause is confirmed and it is
**environmental**: the self-hosted `-latin.woff2` subsets follow the Google/fontsource `latin`
unicode-range, which covers U+2191/2192/2193 but not **U+2190**, and the audit container's only
fallback font — the `Open Sans` bundled with `@sparticuz/chromium` — was inspected with `fontTools`
and also lacks U+2190 (1010 codepoints, `0x2190` absent). A real browser falls back through
`system-ui → -apple-system → Segoe UI → Roboto → Helvetica → Arial`, all of which contain `←`.

This is therefore **not** reported as a production defect and no content change was made for it. It
is recorded so the next visual pass does not rediscover it, and so that if a production screenshot
ever shows it the cause is already narrowed. Cheap insurance if that happens: drop the `&larr;` and
let the label stand alone, or use a glyph the `latin` subset does cover.

### F4 — `og:image` falls back to SVG (tracked and **fixed**: [AIN-844](/AIN/issues/AIN-844))

Independently re-confirmed: the homepage `og:image` is `https://news.lesbass.com/og-image.svg`
(`content-type: image/svg+xml`), which Facebook, X, LinkedIn, Slack and Discord will not render.
Article pages with a raster hero are correct (`og:image`, `og:image:alt`, `twitter:image` all present
and on-origin). Not re-tracked — [AIN-844](/AIN/issues/AIN-844) already owned it, and it was **closed
during this heartbeat** by the companion run in `402b41a` (raster `public/og-image.png` +
`src/lib/ogImage.ts`, plus a new `check-seo` failure on SVG social images and on `og:image` size
claims that disagree with the shipped bytes). The guard in that commit and the base-URL guard below
now live in the same script — merged, `npm run audit` is green with both active.

### F5 — `ai-newsroom.pages.dev` serves a different app (already tracked: [AIN-845](/AIN/issues/AIN-845))

Re-confirmed 2026-10-02 00:38 UTC: `/` returns the Japanese editor dashboard, and `/sitemap.xml`
returns that same HTML with `content-type: text/html` (soft-404). Production never links to it.
Remediation needs Cloudflare Pages access. Not re-tracked.

### F6 — design notes (recorded deliberately, no issues opened)

- **No imagery on listing surfaces.** Homepage, `/articles/` and tag pages render **0** `<img>`;
  only article pages carry artwork. Thumbnails would change the listing rhythm and cost bandwidth
  for little gain at the current cadence — worth a deliberate design decision, not a patch.
- **Footer link height.** Probed link boxes on mobile measure 17–20 px tall (`lesbass`, `Sitemap`,
  `Corrections`, `View all 66 articles →`). `test:mobile` passes and WCAG 2.2 2.5.8 exempts links
  inside a sentence, so this is polish, not a failure.
- **RSS has no `<atom:link rel="self">`.** Every `<link>` / `<guid>` is already canonical; the self
  link would be a nicety, not a fix.
